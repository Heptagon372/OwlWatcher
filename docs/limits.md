# 한계와 실측 기록

설계서가 "실험"으로 표시한 항목, 14장 미결 사항, 그리고 구현하면서 실기기에서 드러난 사실을 한곳에 모은다.
**추측과 실측을 섞지 않는다** — 그게 이 도구가 다루는 등급 모델의 규칙이고, 이 문서에도 같은 규칙을 적용한다.

측정 환경은 둘이다. 개발 기기 한 대와 CI 러너. 아래 "실측" 항목은 전부 그 둘 중
하나에서 나온 관측이며, 설계서 12장의 플랫폼 매트릭스를 돌리기 전까지는 일반화할 수 없다.

| | 개발 기기 | CI 러너 |
|---|---|---|
| 환경 | Windows 11 Pro, build 26200 | GitHub Actions `windows-latest` · `macos-14` · `ubuntu-latest` |
| 권한 | 비관리자, Performance Log Users 아님 | 관리자 |
| 원격 세션 | 아니오 | — |
| TPM | 있음 (CNG Microsoft Platform Crypto Provider) | — |
| 측정 시각 | 2026-08-29 | 2026-08-30 (CI #4, 커밋 `003d791`) |

CI 러너가 개발 기기의 가장 큰 공백을 메웠다 — **관리자 권한**. 개발 기기에서
`ERROR_ACCESS_DENIED` 로 끝났던 ETW 실시간 세션이 거기서는 실제로 열린다.

## 1. 캡처 차단 (S13) — 판정 기준을 처음에 틀렸다

**실측: 이 기기에서 `WDA_EXCLUDEFROMCAPTURE` 는 동작한다.** 대조군 센티넬 100.0% → 차단 후 0.0%.

그런데 처음 구현한 자가검증은 이 기기에서 100% 실패를 보고했다. 환경 문제가 아니라 판정 기준이 틀렸다.

| 플래그 | 캡처 결과 |
|---|---|
| `WDA_MONITOR` | 창이 **내용 없이(검게)** 나타난다 |
| `WDA_EXCLUDEFROMCAPTURE` | 창이 **아예 없다** → 창 뒤의 배경이 찍힌다 |

즉 제대로 차단된 캡처는 검은 화면이 아니라 바탕화면이다. "균일한 검정인가"로 보면 정상 동작을 영원히
실패로 읽는다. 지금은 시험 창이 칠한 고유색(센티넬 `#0BF58C`)이 캡처에 나타나는지를 본다 —
확인하려는 것이 색이 아니라 "우리 창 내용이 캡처에 새는가"이기 때문에, 두 플래그와 앞으로 나올
다른 차단 방식에도 그대로 통한다.

**교훈**: 이 종류의 오류는 픽스처 테스트로 안 잡힌다. 실기기에서 돌려야만 나온다.

### 아직 확인하지 못한 캡처 경로 (설계서 14장 미결 4번)

`--capture-test` 는 커닝 도구가 흔히 쓰는 **GDI BitBlt** 경로 하나만 확인한다. 아래는 미확인이다.

- DWM 하위에서 합성 결과를 직접 가져가는 경로
- Windows.Graphics.Capture (WinRT) — 이론상 차단되지만 실측 안 함
- 하드웨어 캡처 카드 (HDMI 스플리터) — 소프트웨어로 막을 수 없다
- 원격 데스크톱 세션 — 코드가 `SM_REMOTESESSION` 을 읽어 진단에 표기하지만, 실제 동작은 미측정
- 가상 디스플레이 드라이버

설계서 12장의 "차단 검증" 항목(PrintScreen · Snipping Tool · OBS 각각으로 확인)은 사람이 눈으로 해야 한다.
`owlwatch-agent` 를 띄워 놓고 각 도구로 찍어 본 뒤, 비지 않는 경로가 있으면 여기 추가한다.

## 2. Windows LED 전용 제어 (설계서 14장 미결 3번)

**실측: 이 기기에서는 비관리자 앱이 키보드 LED 출력 리포트를 보내지 못했다.**

`owlwatch-sim c --confirm` 결과:

| 항목 | 값 |
|---|---|
| HID 인터페이스 | 14개 |
| 키보드 사용 페이지(0x01/0x06) | 2개 |
| 읽기/쓰기로 열린 것 | 14개 |
| `HidD_SetOutputReport` 성공 | **0개** |

→ 설계서 05장 S12 의 Windows 칸에 적힌 전제("실사용 도구는 실제 Caps Lock 상태를 토글하게 되고,
그건 S4 폴링이 확정 관측")가 **이 기기에서는 유지된다.**

다만 이건 한 기기의 결과다. 게이밍 키보드처럼 자체 HID 인터페이스를 노출하는 장치, 또는 벤더
드라이버가 있는 환경에서는 달라질 수 있다. 매트릭스를 돌려야 답이 확정된다.

주의: HID 장치를 **여는 것 자체**는 14개 전부 성공했다. macOS 라면 그 오픈이 `NOTIFY_IOKIT_OPEN`
으로 그대로 기록되지만(S12, P0), Windows 에는 대응 관측이 없다. 이 비대칭은 남아 있다.

## 3. 프로세스 원장 (S9) — 커널 경로는 구현됐고, 남은 것은 권한이다

ETW `Microsoft-Windows-Kernel-Process` 실시간 세션을 raw P/Invoke 로 구현했다
(NuGet TraceEvent 패키지를 쓰지 않는다 — 저장소 전체가 의존성 0 이다).

**실측 1 (개발 기기, 비관리자): 세션을 열 수 없다.**

```
관리자: False · Performance Log Users: False
StartTrace → ERROR_ACCESS_DENIED (Win32 5)
```

**실측 2 (CI 러너, 관리자): 커널 원장이 동작한다.**

CI 의 Windows 잡이 엄격 모드로 통과했다.

```
--etw --require-session       실시간 세션이 열리지 않으면 실패
--ledger --require-kernel     커널 원장으로 돌지 못하면 실패
```

두 스텝이 통과했다는 것은 **StartTrace 가 성공했고, 실제로 띄운 프로세스의 exec 관측이
`source=kernel` 로 나왔고, 규칙 엔진이 그것을 P0/crit 으로 판정했다**는 뜻이다.
설계서가 M3 에 걸어 둔 "여기서 Windows 가 P0 등급에 도달한다"가 실측으로 확인됐다.

한 가지 주의. 처음 CI 는 이 두 스텝이 **폴백 경로에서도 통과**하도록 되어 있었다.
`--etw` 는 세션 개시 실패를 보고만 하고 실패로 치지 않았다. 그 상태의 초록불은
"커널이 동작한다"를 증명하지 못했고, 그걸 증명으로 읽었다면 이 문서 전체가 거짓이 됐을 것이다.
엄격 모드는 그래서 있다.

권한 없이 검증할 수 있는 것은 전부 검증했다 (`--etw`):

| 검사 | 결과 |
|---|---|
| 구조체 레이아웃 11종 (x64) | 통과 |
| TDH 매니페스트 조회 — ProcessStart · ProcessStop · ImageLoad | 3/3 해석 |
| 원장이 읽는 속성이 매니페스트에 있는가 | `ProcessID` · `ImageName` · `ParentProcessID` 확인 |
| 실시간 세션 개시 | ACCESS_DENIED |

매니페스트가 해석된다는 것은 `EVENT_RECORD` 레이아웃과 tdh.dll P/Invoke 가 맞다는
**독립적 증거**다. 실제 세션에서 남는 미검증 변수는 "커널이 실제로 이벤트를 보내는가" 하나뿐이다.

레이아웃 검사는 제 기대값이 틀렸을 때도 신호를 냈다 — `EVENT_TRACE_PROPERTIES` 를 128,
`EVENT_RECORD` 를 104 로 잘못 적었고 실제는 120·112 였다. 검사가 구현이 아니라 기대값을
잡아낼 수도 있다는 뜻이라, 2번(TDH 해석)이 함께 있어야 한다.

### 권한이 없을 때 실제로 무슨 일이 일어나는가 — 전 구간 실측

`--ledger` 는 실제로 프로세스를 하나 띄우고 원장이 그것을 본 뒤 규칙 엔진까지 통과시킨다.

```
원장: fallback (커널 세션 ACCESS_DENIED)
exec 관측 — source=userspace collector=process-diff-poll degraded
P1/warn [정황] … ~/…/owlwatch-specrunner.exe 실행(미서명, 사용자 공간 열거)
강등 이유: "출처가 userspace(부분 실패) 이므로 등급을 P0에서 P1로 낮춤.
            커널·서버·자가검증이 아닌 근거는 결정적이지 않다."
```

**등급이 출처를 정직하게 따라간다는 것이 실측으로 확인됐다.** 이게 등급 모델의 전부다 —
깨지면 나머지가 전부 거짓말이 된다.

설계서 14장 미결 2번은 **절반만 답했다.** 관리자면 된다는 것은 확인됐고,
**Performance Log Users 그룹만으로 충분한지는 여전히 미확인**이다 — 그 그룹에 계정을 넣은
환경에서 `--etw --require-session` 을 돌려야 답이 나온다. 학교 이미지에 그룹을 미리 넣을 수
있는지도 함께 확인해야 한다. 실전에서는 이쪽이 관리자보다 현실적인 배포 경로다.

## 4. 트레이 항목 소유자 (S2) — 레지스트리만으로는 부족하다

`HKCU\Control Panel\NotifyIconSettings` 는 **한 번이라도 아이콘을 띄운 앱의 설정을 남겨 둔다.**
지운 앱의 항목도 그대로 있어서, 그것만 읽으면 "지금 없는 아이콘"으로 오탐이 난다.
그래서 레지스트리 항목과 **현재 실행 중인 프로세스의 교집합**만 관측으로 낸다.

라이브 트레이 툴바는 버튼 **개수만** 읽는다. 버튼의 `dwData` 를 따라가 소유 창을 알아내는 방법은
문서화되지 않은 셸 내부 구조체에 의존해 Windows 빌드마다 깨지고, **틀린 pid 를 조용히 만들어 낸다.**
P0 근거를 다루는 도구에서 그건 최악의 실패라 구현하지 않았다. 대신 개수 차이를 `degraded` 와
수집기 노트로 남긴다 — "레지스트리로 설명되지 않는 아이콘이 떠 있다"는 사실은 전달되고,
소유자를 추측하지는 않는다.

**결과적으로 남는 구멍**: 레지스트리에 항목을 만들지 않는 트레이 아이콘은 소유자를 특정하지 못한다.
S1(에이전트형 프로세스)이 보조로 잡는다.

## 5. 에이전트형 프로세스 (S1) — Windows 에는 대응 개념이 없다

macOS 는 `NSWorkspace.runningApplications` 의 `activationPolicy` 가 `.accessory`/`.prohibited`
로 답을 준다. Windows 에는 없다.

처음에 "보이는 창이 없는 프로세스"로 잡았더니 실기기에서 `conhost` · `ctfmon` · `sihost` ·
`cmd` · `bash` · `node` 까지 **수십 건이 걸렸다.** 지금은 좁혔다 —
**최상위 창을 하나라도 만들었지만 보이는 창은 하나도 없는 프로세스.**
콘솔 프로그램은 자기 최상위 창이 없어(콘솔 창은 conhost 소유) 자연히 빠진다.

**남는 구멍**: 메시지 전용 창(`HWND_MESSAGE`)만 가진 도구는 이 조건에서 빠질 수 있다.
그런 도구가 트레이 아이콘을 띄우면 S2 가 잡고, 실행 순간은 S9 가 잡는다 — 세 신호가 서로의 사각을 메운다.

## 6. 서명 검증 — 카탈로그를 빼먹으면 전부 미서명이 된다

Windows 시스템 바이너리 대부분은 파일에 서명이 박혀 있지 않고 **`.cat` 카탈로그로 서명**된다.
임베디드 서명만 확인하면 `conhost.exe` · `ctfmon.exe` · `sihost.exe` 가 전부 "미서명"으로 나오고
좌석마다 수십 건의 오탐이 된다. 실기기에서 바로 드러난 문제라 `CryptCATAdmin*` 경로를 추가했다.

`is_platform_binary` 의 Windows 대응물은 **Windows 디렉터리 안 + Microsoft Windows 서명**의 AND 로 잡았다.
서명자만 보면 위장에 약하고, 경로만 보면 시스템 폴더에 떨군 파일이 통과한다.

## 7. VM 탐지 (S6) — 하이퍼바이저 비트만으로는 오탐이 난다

Windows 11 은 VBS/HVCI 가 기본으로 켜져 있어 **실기기에서도 하이퍼바이저 위에서 돈다.**
CPUID leaf 1 ECX 비트 31 은 켜져 있고 벤더 문자열은 `Microsoft Hv` 가 나온다.
그대로 두면 노트북 대부분이 "VM 응시"로 잡힌다 — 실기기에서 실제로 그렇게 나왔다.

지금은 CPUID 비트를 사실 그대로 `hypervisorPresent` 로 두고, 규칙이 쓰는 값은
SMBIOS 제조사·모델을 함께 본 `vmGuestLikely` 로 따로 낸다.

**남는 한계**: 중첩 가상화, 베어메탈 위장(SMBIOS 를 실기기처럼 꾸민 VM)은 못 잡는다. 설계서 11장에 이미 명시돼 있다.

## 8. 소프트웨어 키 폴백 (S14)

TPM 이 없으면 소프트웨어 키로 폴백하고 `attestation: "sw"` 로 보고한다. 이 키는 **기기를 증명하지 못한다** —
키 파일을 복사하면 그만이다. 그래서 평문으로 저장한다: 복사되면 끝인 키를 "보호된 것처럼" 보이게 하는 쪽이 더 위험하다.
콘솔 UI 와 학생 화면에 그대로 표기하고, 등급을 낮춰 다룬다.

이 기기에서는 TPM 이 잡혔으므로 폴백 경로는 **실측하지 못했다.**

## 9. 범위 밖 — 소프트웨어로 못 막는 것

설계서 00장 비목표 그대로다. 콘솔 첫 화면과 학교 제안서에 이 문장을 그대로 넣는다.

- 휴대폰 · 2차 기기 · AI 안경
- 핫스팟 우회 (S5 canary 가 **탐지**는 하지만 기기 두 대를 쓰면 통제 밖)
- 하드웨어 캡처 카드
- 어깨너머 보기, 종이 쪽지 — 감독의 영역

> OwlWatch 는 커닝을 불가능하게 만드는 도구가 아니라, 노트북 상주형 도구의 비용과 발각 확률을
> 크게 올리고, 발각됐을 때 다툴 수 없는 근거를 남기는 도구다.

## 10. L2 락다운 (Take a Test) — 이 기기에서 가용

**실측: 쓸 수 있다.**

| 항목 | 결과 |
|---|---|
| `ms-edu-secureassessment` 프로토콜 | 등록됨 |
| `Microsoft.Windows.SecureAssessmentBrowser` | 10.0.26100.1 |

승인이 필요 없다는 것이 macOS AAC 와의 결정적 차이다 — Windows 는 오늘 켤 수 있다.

**진입은 실측하지 않았다.** 실행하면 화면 전체가 잠금 모드로 바뀌어 개발 기기를 뺏기므로,
가용성 확인까지만 했다. 진입·이탈(S7) 동작은 실기기 파일럿에서 확인해야 한다.

한계는 설계서 06장 그대로다 — **백그라운드 프로세스는 계속 돈다.** 볼 화면이 없어 무력할 뿐이고,
그래서 진입 전 L0 스캔을 강제하고 창이 사라지면 S7 crit 를 낸다.

## 11. 아직 검증되지 않은 것

코드가 있는 것과 동작이 확인된 것은 다르다. 아래는 **코드는 있으나 미검증**이다.

| 항목 | 상태 |
|---|---|
| macOS 수집기 (ESF · AAC · 사용자 공간) | **한 번도 컴파일되지 않았다.** `ES_EVENT_TYPE_NOTIFY_TCC_MODIFY` 가 macOS 15.4 SDK 심볼이라 CI 러너(macos-14)에서 짓지 않는다. 엔타이틀먼트와 Xcode 프로젝트가 선결이다 |
| 콘솔 (Next.js + Supabase) | 빌드·타입체크 통과. **실 Supabase 프로젝트 연결·RLS·트리거 동작 미검증** |
| L2 진입·이탈 | 가용성만 확인. 진입 미실행 (실행하면 화면 전체가 잠긴다) |
| Take a Test 안에서의 S7 탐지 | 미검증 |
| Performance Log Users 만으로 ETW 세션 | 미검증 (관리자면 된다는 것만 확인) |

## 13. 설계서와 다르게 구현한 것

| 항목 | 설계서 | 구현 | 이유 |
|---|---|---|---|
| S5 beacon 실패 등급 | P1 (심각도 info) | **P2** (심각도 info) | 비콘 실패는 학교망 장애와 구분되지 않는다. "단독으로는 아무 의미 없음"이라는 P2 정의에 정확히 맞는다. 심각도는 설계서대로 info. |
| S8 에이전트 무결성 | P1 | P1 (설계서대로) | 자가검증이라 형식상 P0 요건을 만족하지만 카탈로그가 P1 로 둔다. **서명된 바이너리를 패치하면 무결성 검사도 함께 패치되므로** 결정적이라고 말할 수 없다 — 설계서가 맞다고 보고 따랐다. |
| LMS 표시 | WebView2 | 자리표시 패널 | WebView2 는 NuGet 패키지와 런타임 배포가 필요해 M1 의 "의존성 0" 방침과 충돌한다. 통합 지점은 `ExamWindow.BuildExamSurface` 에 표시해 뒀다. |

**의도적으로 허용목록에 넣지 않은 것**: Anthropic PBC(AI 어시스턴트), Riot Games(게임 클라이언트),
Ollama·Python(미서명 로컬 실행 환경), Wondershare. 실기기 오탐 코퍼스에서 나왔지만 시험에서는
이것들이 잡히는 게 맞다. 허용목록은 오탐을 줄이는 도구이지 조용하게 만드는 도구가 아니다.
